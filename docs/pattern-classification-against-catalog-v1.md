# `pattern-classification` — Pattern Classification Against Catalog

## 1. Purpose

`pattern-classification` classifies each project fingerprint produced by `application-fingerprinting` against a master catalog of known application patterns.

`application-fingerprinting` answers:

> What technical signals were observed for this project?

`pattern-classification` answers:

> Which known application pattern, or combination of patterns, is supported by those signals?

The overall flow is:

```text
solution-discovery — Solution and Project Discovery
        ↓
application-fingerprinting — Application Fingerprinting
        ↓
pattern-classification — Pattern Classification Against Catalog
        ↓
pattern-discovery-clustering — Pattern Discovery and Clustering for Unmatched Applications
```

`pattern-classification` must not rescan the repository. It should operate only on the normalized fingerprint and signals generated by `application-fingerprinting`.

---

## 2. Current Design Challenge

The catalog currently contains `detection_rules` based on:

- Namespaces
- File globs
- Package names

These rules were created before `application-fingerprinting` introduced normalized fingerprint signals.

`application-fingerprinting` now produces registered signal names, along with:

- Signal category
- Signal type
- Signal value
- Occurrence count
- Extraction confidence
- Source type
- Source path
- Evidence
- Extractor name

The catalog should therefore evolve from raw repository-oriented rules to signal-oriented rules.

Existing style:

```yaml
namespaces:
  - Microsoft.AspNetCore.Mvc*

fileGlobs:
  - "**/Controllers/*.cs"

packages:
  - Microsoft.AspNetCore.Mvc
```

Recommended style:

```yaml
signals:
  - name: MICROSOFT_ASPNETCORE_MVC_NAMESPACE
  - name: CONTROLLERS_FOLDER
  - name: MICROSOFT_ASPNETCORE_PACKAGE
```

The eight existing seeded patterns will need to be revised to use registered `application-fingerprinting` signal names.

---

## 3. Input from `application-fingerprinting`

`pattern-classification` should process one project fingerprint at a time.

An `application-fingerprinting` project fingerprint contains information such as:

```json
{
  "projectId": "project-001",
  "projectPath": "src/PublicApi/PublicApi.csproj",
  "fingerprintStatus": "PARTIAL",
  "analysisCapabilities": {
    "configurationParsed": true,
    "deploymentArtifactsParsed": false,
    "fileDiscovery": true,
    "generatedCodeExcluded": true,
    "msbuildEvaluated": false,
    "projectMetadataParsed": false,
    "semanticAnalysis": false,
    "syntaxAnalysis": true
  },
  "signals": [],
  "warnings": []
}
```

Each signal has a normalized structure:

```json
{
  "category": "FRAMEWORK_REFERENCE",
  "name": "MICROSOFT_ASPNETCORE_NAMESPACE",
  "type": "NAMESPACE",
  "value": "Microsoft.AspNetCore.Components",
  "occurrenceCount": 1,
  "extractionConfidence": 1.0,
  "sourceType": "SOURCE_CODE",
  "sourcePath": "src/BlazorAdmin/Helpers/BlazorComponent.cs",
  "extractor": "FrameworkReferenceExtractor",
  "evidence": []
}
```

`pattern-classification` should use the stable signal name as the primary classification input while optionally using the other fields for more precise rule conditions.

## 4. Processing Unit

The primary processing unit for `pattern-classification` should be:

```text
One project fingerprint
```

Recommended outer loop:

```text
For each project fingerprint
    Validate classification eligibility
    Normalize and aggregate project signals
    Identify candidate catalog patterns
    Evaluate candidate detection rules
    Score and rank matches
    Resolve compatible and conflicting patterns
    Produce classification output
```

Classification should not be performed signal by signal in isolation because one signal often supports multiple possible application patterns.

For example:

```text
RAZOR_FILE
```

may appear in:

- Blazor WebAssembly
- Blazor Server
- Razor Pages
- ASP.NET Core MVC

Similarly:

```text
MICROSOFT_ASPNETCORE_NAMESPACE
```

may appear in:

- REST API projects
- MVC applications
- Blazor applications
- Authentication libraries
- Infrastructure projects
- Functional-test projects

A reliable classification requires evaluating a combination of signals.

---

## 5. Evaluation Direction

Two possible evaluation directions exist.

### 5.1 Signal-First Evaluation

```text
For each project
    For each signal
        Find patterns that reference that signal
```

This is useful for:

- Candidate-pattern lookup
- Catalog coverage reporting
- Finding signals unused by the catalog
- Performance optimization

However, signal-first evaluation should not be the authoritative classification algorithm because individual signals are often ambiguous.

### 5.2 Pattern-First Evaluation

```text
For each project
    For each eligible pattern
        Evaluate the complete detection rule against project signals
```

This supports:

- Required signal combinations
- Optional supporting evidence
- Exclusion rules
- Negative evidence
- Pattern confidence
- Explainable classification
- Multiple pattern matches
- Conflict resolution

### 5.3 Recommended Hybrid

Use:

> Pattern-driven evaluation with signal-based indexing.

Recommended flow:

```text
Project fingerprint
        ↓
Normalized signal index
        ↓
Signal-to-pattern inverted index
        ↓
Candidate patterns
        ↓
Complete pattern-rule evaluation
        ↓
Scoring and conflict resolution
        ↓
Classification result
```

The responsibilities are:

| Direction | Responsibility |
|---|---|
| Signal → Pattern | Candidate lookup and catalog coverage |
| Pattern → Signals | Authoritative classification |

## 6. Signal Indexing

Before evaluating patterns, `pattern-classification` should normalize and aggregate project signals.

Example internal indexes:

```text
signalsByName["RAZOR_FILE"] → 13 occurrences

signalsByName["MICROSOFT_ASPNETCORE_PACKAGE"] → 4 occurrences

signalsByNameAndValue[
  "MICROSOFT_ASPNETCORE_PACKAGE",
  "Microsoft.AspNetCore.Components.WebAssembly"
] → 1 occurrence
```

The index should preserve:

- Total occurrence count
- Distinct values
- Distinct source files
- Maximum and average extraction confidence
- Original evidence
- Signal categories
- Source types

Duplicate signals should not be discarded. They should be aggregated while retaining the original evidence records.

---

## 7. Candidate Pattern Selection

`pattern-classification` should avoid evaluating every catalog pattern unnecessarily once the catalog grows.

Each pattern should define one or more discriminating `anchorSignals`.

Example:

```yaml
patternId: blazor-webassembly
anchorSignals:
  - RAZOR_FILE
  - MICROSOFT_ASPNETCORE_PACKAGE
  - WEB_APPLICATION_CREATE_BUILDER_ENTRY_POINT
```

The signal-to-pattern index can use these anchor signals to identify relevant candidate patterns.

Weak or generic signals should not be used as the only anchor.

Examples of weak signals:

```text
PROGRAM_CS_FILE
SERVICES_FOLDER
MICROSOFT_ASPNETCORE_NAMESPACE
CONNECTION_STRING_CONFIG
```

These can be supporting evidence, but they should not independently make a pattern a candidate unless combined with stronger evidence.

## 8. Recommended Detection-Rule Structure

A catalog rule should support:

- Eligibility
- Anchor signals
- Required evidence
- Alternative evidence
- Supporting evidence
- Negative evidence
- Analysis requirements
- Scoring thresholds
- Compatibility and conflict metadata

Example:

```yaml
patternId: aspnet-core-rest-api
patternVersion: 2.0.0
displayName: ASP.NET Core REST API

scope: PROJECT

classification:
  role: PRIMARY
  family: APPLICATION_TYPE
  value: REST_API

priority: 80

eligibility:
  fingerprintStatuses:
    - COMPLETE
    - PARTIAL
  excludedProjectRoles:
    - TEST
    - DEPLOYMENT

anchorSignals:
  - WEB_APPLICATION_CREATE_BUILDER_ENTRY_POINT
  - API_CONTROLLER_ATTRIBUTE
  - ROUTE_ATTRIBUTE

analysisRequirements:
  required:
    syntaxAnalysis: true
  preferred:
    projectMetadataParsed: true
    semanticAnalysis: true

detectionRules:
  all:
    - signal:
        name: WEB_APPLICATION_CREATE_BUILDER_ENTRY_POINT
        minimumOccurrences: 1

  any:
    - signal:
        name: API_CONTROLLER_ATTRIBUTE
        minimumOccurrences: 1
    - signal:
        name: CONTROLLER_BASE_CLASS
        minimumOccurrences: 1
    - signal:
        name: ROUTE_ATTRIBUTE
        minimumOccurrences: 1

  supporting:
    - signal:
        name: HTTP_GET_ATTRIBUTE
        weight: 10
    - signal:
        name: HTTP_POST_ATTRIBUTE
        weight: 10
    - signal:
        name: MICROSOFT_ASPNETCORE_MVC_NAMESPACE
        weight: 10
    - signal:
        name: CONTROLLERS_FOLDER
        weight: 5

  none:
    - signal:
        name: FACT_ATTRIBUTE
        minimumOccurrences: 1
    - signal:
        name: TEST_METHOD_ATTRIBUTE
        minimumOccurrences: 1

thresholds:
  minimumScore: 70
  highConfidenceScore: 90
```

## 9. Signal Condition Structure

Rules should primarily reference signal names but may apply additional conditions.

Supported signal fields should include:

- `name`
- `category`
- `type`
- `value`
- `sourceType`
- `occurrenceCount`
- `extractionConfidence`
- `sourcePath`

Example using a package value:

```yaml
- signal:
    name: MICROSOFT_ASPNETCORE_PACKAGE
    value:
      equals: Microsoft.AspNetCore.Components.WebAssembly
    minimumOccurrences: 1
```

Example using a namespace prefix:

```yaml
- signal:
    name: MICROSOFT_ASPNETCORE_NAMESPACE
    value:
      startsWith: Microsoft.AspNetCore.Components
    minimumOccurrences: 2
```

Example using occurrence count:

```yaml
- signal:
    name: RAZOR_FILE
    minimumOccurrences: 3
    minimumExtractionConfidence: 0.90
```

This is important because some canonical signal names are intentionally broad, while the `value` field identifies the precise framework, package, namespace, endpoint, or configuration element.

## 10. Required Rule Operators

The catalog rule language should support the following operators.

### 10.1 Boolean Composition

```text
all
any
none
atLeast
```

Example:

```yaml
all:
  - signal:
      name: SERVICE_CONTRACT_ATTRIBUTE
  - signal:
      name: OPERATION_CONTRACT_ATTRIBUTE
```

Example:

```yaml
any:
  - signal:
      name: SVC_FILE
  - signal:
      name: SYSTEM_SERVICE_MODEL_CONFIG
```

Example:

```yaml
none:
  - signal:
      name: TEST_METHOD_ATTRIBUTE
```

Example:

```yaml
atLeast:
  count: 2
  of:
    - signal:
        name: RAZOR_FILE
    - signal:
        name: PAGES_FOLDER
    - signal:
        name: MICROSOFT_ASPNETCORE_PACKAGE
```

### 10.2 Quantitative Conditions

```text
exists
minimumOccurrences
maximumOccurrences
minimumDistinctValues
minimumDistinctSourceFiles
```

### 10.3 Value Matching

```text
equals
in
startsWith
contains
regex
```

Exact, prefix, and membership matching should be preferred over regex wherever possible.

### 10.4 Confidence Conditions

```text
minimumExtractionConfidence
```

### 10.5 Analysis-Capability Conditions

```text
requires syntax analysis
requires semantic analysis
requires configuration parsing
requires MSBuild evaluation
requires project metadata
```

### 10.6 Project Metadata Conditions

Some conditions may need to use fingerprint metadata directly:

```text
projectSdk
outputType
targetFramework
projectFormat
fingerprintStatus
analysisCapabilities
```

Not every property needs to be converted into a registered signal.

## 11. Project Role Classification

`pattern-classification` should avoid treating every project as a deployable application.

Recommended classification layers:

```text
Layer 1 — Project Role
    Application
    Test
    Library
    Database
    Deployment
    Unknown

Layer 2 — Primary Application Pattern
    REST API
    WCF Service
    MVC Web Application
    Blazor Application
    Batch Application
    Windows Service
    etc.

Layer 3 — Secondary Technical Capabilities
    Entity Framework Core
    Message Consumer
    Scheduled Processing
    WCF Client
    Containerized
    Authentication
```

A test project may contain ASP.NET Core, MVC, or Entity Framework signals because it tests those technologies.

Example:

```json
{
  "projectRole": "TEST",
  "primaryApplicationPattern": null,
  "secondaryCapabilities": [
    "ASP_NET_CORE_TEST_HOST",
    "ENTITY_FRAMEWORK_TESTING"
  ]
}
```

It should not normally be classified as a production web application.

Project-role rules can either:

1. Run before application-pattern classification, or
2. Be stored as a separate catalog pattern family with a higher evaluation priority.

The first approach is simpler and recommended.

## 12. Multiple Pattern Matches

A project may legitimately match more than one pattern.

Examples:

```text
ASP.NET Core MVC
REST API
Background Processing
SignalR Host
Authentication Provider
```

`pattern-classification` should distinguish between:

### Primary Patterns

Describe the main runtime or workload:

```text
REST_API
MVC_WEB_APPLICATION
BLAZOR_WEBASSEMBLY
WINDOWS_SERVICE
BATCH_APPLICATION
```

### Secondary Patterns or Capabilities

Describe supporting technical characteristics:

```text
ENTITY_FRAMEWORK_CORE
MESSAGE_CONSUMER
SCHEDULED_PROCESSING
WCF_CLIENT
CONTAINERIZED
```

### Mutually Exclusive Patterns

Examples:

```text
BLAZOR_WEBASSEMBLY
BLAZOR_SERVER
```

### Compatible Patterns

Examples:

```text
ASP_NET_CORE_MVC
REST_API
```

The catalog should store compatibility metadata.

Example:

```yaml
classification:
  role: PRIMARY
  family: WEB_APPLICATION

compatibility:
  compatibleWith:
    - REST_API
  conflictsWith:
    - BLAZOR_SERVER
```

## 13. Classification Algorithm

### Phase 1 — Load and Validate Catalog

- Validate pattern schema.
- Validate signal names against the registered signal catalog.
- Reject or quarantine patterns referencing unknown signals.
- Validate pattern IDs and versions.
- Validate thresholds and weights.
- Validate compatibility and conflict declarations.
- Detect duplicate or unreachable rules.
- Build the signal-to-pattern inverted index.

### Phase 2 — Prepare Project Fingerprint

- Skip fingerprints with status `SKIPPED`.
- Process `COMPLETE` and `PARTIAL` fingerprints.
- Normalize and aggregate signals.
- Preserve evidence.
- Identify project role or role hints.
- Record available analysis capabilities.
- Record fingerprint completeness.

### Phase 3 — Find Candidate Patterns

- Use anchor signals and the inverted index.
- Exclude patterns that fail basic eligibility.
- Exclude application patterns for test, deployment, or unsupported projects.
- Avoid selecting candidates based only on generic signals.

### Phase 4 — Evaluate Rules

For each candidate pattern:

- Evaluate required conditions.
- Evaluate alternative conditions.
- Evaluate supporting conditions.
- Evaluate negative conditions.
- Evaluate project metadata conditions.
- Check required analysis capabilities.
- Calculate raw match score.
- Record matched and missing conditions.
- Produce an explanation.

### Phase 5 — Calculate Confidence

- Start with rule match score.
- Apply fingerprint-completeness adjustment.
- Apply extraction-confidence adjustment.
- Apply ambiguity adjustment.
- Apply conflict adjustment.
- Cap confidence when required analysis is unavailable.

### Phase 6 — Resolve Results

- Separate primary and secondary matches.
- Resolve conflicts using catalog priority and confidence.
- Retain ambiguity if evidence does not support a safe winner.
- Do not force one pattern when multiple compatible patterns apply.
- Return `NO_PATTERN_MATCHED` where no rule passes the threshold.

### Phase 7 — Produce Governance Observations

- Registered signals not referenced by any pattern
- Patterns referencing unknown signals
- Patterns never evaluated
- Patterns never matched
- Frequent signal combinations in unmatched projects
- Classification blocked by incomplete fingerprints
- Rules producing repeated ambiguity

## 14. Match Score and Classification Confidence

`pattern-classification` should distinguish between:

```text
Rule Match Score
```

and:

```text
Classification Confidence
```

Example:

```text
Rule match score:          95/100
Fingerprint completeness: 65/100
Final confidence:          78/100
```

A possible model is:

```text
Final confidence =
    Rule evidence score
  × Fingerprint completeness factor
  × Signal extraction confidence factor
  × Ambiguity factor
```

Pattern-specific analysis requirements are important.

Example:

```yaml
analysisRequirements:
  required:
    fileDiscovery: true
    syntaxAnalysis: true

  preferred:
    projectMetadataParsed: true
    semanticAnalysis: true
```

A pattern should not be penalized for unavailable analysis that it does not need.

Examples:

- A Blazor rule based on Razor files and WebAssembly package signals may not require semantic analysis.
- A precise inheritance rule may require semantic analysis.
- A WCF configuration rule may require configuration parsing.

## 15. Scoring Model

A simple configurable scoring model can use:

### Required Conditions

Failure means the pattern does not match.

```yaml
all:
  - signal:
      name: SERVICE_CONTRACT_ATTRIBUTE
```

### Alternative Conditions

At least one must match.

```yaml
any:
  - signal:
      name: SVC_FILE
  - signal:
      name: SYSTEM_SERVICE_MODEL_CONFIG
```

### Supporting Conditions

Add score but do not independently establish a match.

```yaml
supporting:
  - signal:
      name: OPERATION_CONTRACT_ATTRIBUTE
    weight: 15
```

### Negative Conditions

Reduce score or disqualify the pattern.

```yaml
none:
  - signal:
      name: FACT_ATTRIBUTE
```

### Example Score Calculation

```text
Required conditions passed:          eligible
Anchor signals:                      30
Supporting source signals:           25
Supporting configuration signals:    20
Supporting package signals:          10
Preferred semantic evidence missing: -5
Test-related conflicting signal:     -20
------------------------------------------------
Raw match score:                     60
Minimum threshold:                   70
Result:                              Not matched
```

Weights and thresholds should remain configurable per pattern.

## 16. Classification Statuses

Recommended project-level statuses:

```text
MATCHED
MULTIPLE_MATCHES
AMBIGUOUS
NO_PATTERN_MATCHED
INSUFFICIENT_FINGERPRINT
NOT_ELIGIBLE
SKIPPED
CLASSIFICATION_FAILED
```

### `MATCHED`

One or more compatible patterns passed the threshold.

### `MULTIPLE_MATCHES`

Several compatible primary or secondary patterns matched.

### `AMBIGUOUS`

Conflicting patterns achieved similar scores and no safe winner could be selected.

### `NO_PATTERN_MATCHED`

The fingerprint was sufficiently complete, but no catalog pattern passed the threshold.

This project can become a `pattern-discovery-clustering` candidate.

### `INSUFFICIENT_FINGERPRINT`

Required analysis was unavailable or the fingerprint lacked enough evidence.

This should usually be retried or reviewed before `pattern-discovery-clustering`.

### `NOT_ELIGIBLE`

The project is outside the scope of the requested pattern family, such as a deployment project or a test project.

### `SKIPPED`

The input fingerprint itself was skipped.

### `CLASSIFICATION_FAILED`

An unexpected rule-engine or catalog-processing error occurred.

## 17. Warning Design

Not every signal that lacks a catalog rule should generate a warning on every project.

Some signals are:

- Generic
- Supporting
- Cross-cutting
- Contextual
- Reserved for future patterns
- Useful for modernization analysis rather than application classification

Examples:

```text
CONNECTION_STRING_CONFIG
SERVICES_FOLDER
MICROSOFT_ENTITYFRAMEWORKCORE_NAMESPACE
DB_CONTEXT_BASE_CLASS
```

These may describe technical capabilities without defining the primary application pattern.

Warnings should be divided into two groups.

### 17.1 Project Classification Warnings

```text
NO_PATTERN_MATCHED
AMBIGUOUS_PATTERN_MATCH
INSUFFICIENT_REQUIRED_SIGNALS
CLASSIFICATION_CONFIDENCE_CAPPED
FINGERPRINT_PARTIAL
CONFLICTING_PRIMARY_PATTERNS
REQUIRED_ANALYSIS_UNAVAILABLE
```

### 17.2 Catalog Governance Observations

```text
REGISTERED_SIGNAL_NOT_USED_BY_ANY_PATTERN
PATTERN_REFERENCES_UNKNOWN_SIGNAL
PATTERN_RULE_NEVER_MATCHED
SIGNAL_FREQUENTLY_PRESENT_IN_UNMATCHED_PROJECTS
SIGNAL_REGISTRY_VERSION_MISMATCH
PATTERN_CONFLICT_CONFIGURATION_INVALID
```

Unused registered signals should normally appear in a catalog-coverage report rather than as repeated project warnings.

## 18. Catalog Governance

`pattern-classification` should produce catalog-health metrics in addition to project classifications.

Recommended metrics:

- Total registered signals
- Signals referenced by at least one pattern
- Signals not referenced by any pattern
- Total active patterns
- Patterns evaluated
- Patterns matched
- Patterns never matched
- Rules referencing unknown signals
- Most common unmatched signals
- Most common unmatched signal combinations
- Patterns producing the most ambiguous results
- Patterns producing the most false-positive review findings
- Catalog version used for each scan

Example:

```text
Registered signals:                  87
Signals referenced by catalog:       54
Signals not referenced:              33
Active patterns:                      8
Patterns matched in latest scan:      6
```

## 20. Explainability Requirements

Every classification should explain:

- Which pattern was evaluated
- Which required rules matched
- Which supporting rules matched
- Which preferred signals were missing
- Which negative rules triggered
- Which analysis capabilities were unavailable
- How the match score was calculated
- Why the confidence was reduced
- Why a conflicting pattern was rejected

Example:

```text
Matched pattern:
ASP.NET Core REST API

Primary evidence:
- WEB_APPLICATION_CREATE_BUILDER_ENTRY_POINT
- HTTP_POST_ATTRIBUTE
- MICROSOFT_ASPNETCORE_MVC_NAMESPACE

Supporting evidence:
- PROGRAM_CS_FILE
- CONNECTION_STRING_CONFIG

Missing preferred evidence:
- API_CONTROLLER_ATTRIBUTE

Confidence limitation:
- Semantic analysis was unavailable
```

A user should be able to trace every classification back to the `application-fingerprinting` evidence.

## 21. Migration of the Eight Seeded Patterns

Each existing pattern should be migrated using the following process:

1. Identify existing namespace rules.
2. Identify existing file-glob rules.
3. Identify existing package rules.
4. Map each raw rule to one or more registered signal names.
5. Determine whether signal name alone is sufficient.
6. Add value predicates where broad signal names are used.
7. Identify strong anchor signals.
8. Separate required, alternative, supporting, and negative conditions.
9. Define project-role eligibility.
10. Define required and preferred analysis capabilities.
11. Define primary or secondary classification role.
12. Define compatible and conflicting patterns.
13. Assign weights and thresholds.
14. Create positive test fixtures.
15. Create negative and confusing test fixtures.
16. Validate against real `application-fingerprinting` fingerprint outputs.
17. Review false positives and false negatives.
18. Version and publish the revised pattern.

Example mapping:

| Existing Rule | Recommended Signal Rule |
|---|---|
| Namespace starts with `Microsoft.AspNetCore.Mvc` | `MICROSOFT_ASPNETCORE_MVC_NAMESPACE` |
| File glob `**/*.razor` | `RAZOR_FILE` |
| Package `Microsoft.AspNetCore.Components.WebAssembly` | `MICROSOFT_ASPNETCORE_PACKAGE` with exact value |
| Folder glob `**/Controllers/**` | `CONTROLLERS_FOLDER` |
| Attribute `ApiController` | `API_CONTROLLER_ATTRIBUTE` |
| Base class `ControllerBase` | Registered controller-base signal |
| File glob `**/*.svc` | `SVC_FILE` |
| Attribute `ServiceContract` | `SERVICE_CONTRACT_ATTRIBUTE` |

Before catalog migration, verify that registered signal names are:

- Unique
- Stable
- Clearly documented
- Semantically unambiguous
- Consistently named

## 22. Signal Registry Requirements

The signal registry should be treated as a versioned contract.

Each registered signal should include:

```yaml
name: API_CONTROLLER_ATTRIBUTE
version: 1.0.0
category: SOURCE_CONSTRUCT
type: ATTRIBUTE
description: Indicates usage of the ASP.NET Core ApiController attribute.
valueSemantics: null
deprecated: false
replacement: null
```

For broad signals:

```yaml
name: MICROSOFT_ASPNETCORE_PACKAGE
version: 1.0.0
category: PACKAGE_DEPENDENCY
type: PACKAGE
description: Indicates a Microsoft.AspNetCore package reference.
valueSemantics: Exact package name is stored in the signal value.
deprecated: false
```

Catalog validation must ensure that every referenced signal exists in the expected registry version.

## 23. Testing Strategy

### 23.1 Unit Tests

Test:

- Boolean rule operators
- Value matching
- Occurrence thresholds
- Confidence thresholds
- Negative rules
- Capability requirements
- Score calculation
- Conflict resolution
- Compatibility resolution
- Unknown signal handling

### 23.2 Golden-File Tests

For each seeded pattern, maintain project fingerprints and expected classification output.

Example:

```text
fixtures/
├── blazor-webassembly/
│   ├── fingerprint.json
│   └── expected-classification.json
├── aspnet-core-rest-api/
├── wcf-service/
├── windows-service/
├── webforms-application/
├── mvc-application/
├── batch-application/
└── test-project-with-web-signals/
```

### 23.3 Negative Tests

Include:

- Infrastructure library containing ASP.NET Core namespaces
- Test project containing MVC references
- Shared library containing WCF contracts
- Project with only a `Services` folder
- Project with only `Program.cs`
- Project with partial fingerprint
- Project containing conflicting Blazor indicators
- Project with catalog signal registry mismatch

### 23.4 Regression Tests

Every catalog change should rerun classification against a retained fingerprint corpus.

This allows rule changes without rescanning repositories.

## 26. Out of Scope for `pattern-classification`

`pattern-classification` should not perform:

- Repository scanning
- Source-code parsing
- Signal extraction
- New pattern discovery
- Clustering unmatched projects
- Automatic catalog mutation
- LLM-based pattern invention
- Modernization effort estimation
- Migration-wave planning
- Business application aggregation

These belong to:

```text
application-fingerprinting — Application Fingerprinting
pattern-discovery-clustering — Pattern Discovery and Clustering
Later modernization assessment stages
```

`pattern-classification` may recommend catalog review, but it should not automatically add a new pattern to the master catalog.

---

## 27. Relationship with `pattern-discovery-clustering`

A project should be forwarded to `pattern-discovery-clustering` only when:

```text
classificationStatus = NO_PATTERN_MATCHED
```

and the fingerprint is sufficiently complete.

Projects with:

```text
INSUFFICIENT_FINGERPRINT
```

should normally be retried, enriched, or reviewed before clustering.

`pattern-discovery-clustering` should receive:

- Project identifier
- Aggregated signals
- Signal values
- Signal counts
- Project metadata
- Fingerprint completeness
- Nearest catalog candidates
- Reasons those candidates failed
- Supporting evidence

This prevents `pattern-discovery-clustering` from clustering projects that are unmatched only because analysis was incomplete.

## 28. Key Design Principles

1. **Classify projects, not individual signals.**

2. **Use pattern-driven evaluation for correctness.**

3. **Use signal indexing for candidate selection and governance.**

4. **Store classification logic in the catalog, not in application code.**

5. **Reference canonical signal names rather than rescanning namespaces, files, or packages.**

6. **Allow signal value and count conditions where names are broad.**

7. **Separate primary application patterns from secondary technical capabilities.**

8. **Identify project role before assigning application patterns.**

9. **Support zero, one, or multiple valid matches.**

10. **Do not force a winner when results are ambiguous.**

11. **Distinguish match score from final confidence.**

12. **Reduce confidence when required analysis is unavailable.**

13. **Treat unused signals as catalog-governance observations, not automatic project warnings.**

14. **Make every classification explainable and evidence-backed.**

15. **Version the catalog, signal registry, fingerprint, and classification output.**

16. **Allow catalog reclassification without rescanning source repositories.**

# `pattern-classification` Outcome

> For every eligible project fingerprint, evaluate versioned catalog patterns against the project's normalized signal set, produce zero, one, or multiple explainable pattern classifications, calculate match score and confidence, resolve compatible and conflicting matches, and identify sufficiently complete unmatched projects for `pattern-discovery-clustering`.

## Recommended Technical Direction

> Use a pattern-driven rule engine with a signal-to-pattern inverted index. Reshape the eight seeded catalog patterns so their `detection_rules` reference registered `application-fingerprinting` signal names, with optional filters on signal value, count, category, source, and confidence. Treat the catalog as the authoritative source of classification logic and the signal registry as a versioned contract.
